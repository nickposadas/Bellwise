## What Bellwise is

Subscription hotel software that brings department information together, reduces reporting work, surfaces conflicting evidence, and supports human decisions. The intended deployment runs an open-weight language model within hotel-controlled infrastructure. A subscription pays for the application, connectors, updates, maintenance, and support; a model license alone is not the business.

The experienced director remains responsible for strategy. For example, a marketing director with 20 years of experience proposes ideas; Bellwise reviews supporting evidence and operational constraints, preserves the director's reasoning, and prepares reports for the GM, VPs, and CFO. AI should identify disagreements early instead of silently averaging them away. People can revise, approve, or override recommendations with reasons.

## Current website: implemented vs planned

Implemented in the demo:
- Executive overview and role-perspective selector (GM, VP, CFO), with a computed "Needs attention" table (flagged reports + blocked approvals) instead of a static preview list.

- Housekeeping: dirty -> cleaning -> awaiting inspection -> human confirmation -> ready. Maintenance holds cannot be released through housekeeping or Front Desk.
- Approval queue: approve, return for revision (reason required), or override (reason required). A sample housekeeping conflict must be marked verified before approval.
- Session audit history and CSV export.
- Executive brief generated by a deterministic template, structured into findings / supporting reports / data freshness / decisions required.
- All demo state (reports, tasks, rooms, guest requests, approvals, audit log) persists to this browser's `localStorage` — refreshing does not lose work. An explicit "Reset demo data" action (with a confirmation dialog) clears it and restores the sample data.
- Mobile navigation, responsive layouts (checked at 375/768/1440px, no page-level horizontal overflow), visible keyboard focus rings, and `prefers-reduced-motion` support.

NOT implemented:
- Real AI inference, agents, model serving, or training.
- Live PMS, POS, payroll, accounting, inventory, or marketing connectors.
- A shared/multi-user database — `localStorage` is per-browser only; nothing is synchronized between devices or users, and clearing browser data erases it.
- Application authentication, enforced role permissions, or tenant isolation. The role selector is only a demo perspective, not a security control.
- Subscription billing, licensing, model updates, or local installation tooling.
- External execution of approved recommendations, or a resubmission workflow for a report returned for revision.

Data is synthetic. A downloaded copy runs without the hosted demo's platform-level access restrictions, which is a hosting detail, not application-level authentication — none exists in either case.

## Files and local use

- website/index.html: page shell, nav, topbar, and all `<dialog>` markup. The `.content` div is empty in the markup — `render()` populates every page from JS templates, so there is no separate "static overview" fallback to keep in sync.
- website/bellwise.css: design tokens (`:root` custom properties), layout, and responsive rules.
- website/bellwise.js: data, `localStorage` persistence, rendering, event handling, forms, downloads, audit logic.
- website/fonts/: two self-hosted Source Sans 3 variable-font woff2 files (latin + latin-ext subsets, weights 400–700 in one file per subset). No Google Fonts or other CDN is fetched at runtime.

Open website/index.html in a modern browser. Alternatively, from this folder run `python3 -m http.server 8000 --directory website` and open http://localhost:8000. This is a local development server, not production hosting. No package installation or API key is required. State persists via `localStorage` under the key `bellwise-demo-v1`; delete that key (or use the in-app "Reset demo data") to return to the sample data.

Implementation notes: bellwise.js is the sole active implementation. Business logic (data arrays, mutators, `log()`/`saveState()`) is kept separate from presentation (the `render()`/page-template functions) in the same file — there's no framework or build step, per the brief's "keep current stack" instruction. Many operations use delegated document event handlers. Preserve user-input escaping (`esc()`) if changing rendering; the CSV export also escapes leading `=+@-` characters against formula injection. Acknowledging a report clears its "needs review" flag, which is what drives it out of the Needs Attention table. Role changes do not provide authorization — it's a demo view switch, stated as such in the in-app demo-info dialog.

## Proposed data model and local AI architecture

1. Existing hotel systems and human department inputs supply authorized records.
2. Approved connectors or controlled CSV imports collect only required fields.
3. A local database stores standardized records with hotel, department, source, source record ID, event time, ingestion time, and access scope.
4. Deterministic software checks missing fields, duplicate records, stale updates, inconsistent totals, and conflicting source records. Financial calculations belong in code, not language-model arithmetic.
5. A retrieval layer supplies relevant authorized records to department assistants, with source references. Imported text is data, never permission to execute commands.
6. Initially one shared local open-weight model serves multiple departmental roles with distinct instructions and permitted tools/data. Separate agents do not require separate trained models.
7. Department directors review reports, correct findings, and add context. Preserve original submissions and revisions.
8. An AI Manager combines reviewed reports and flags cross-department conflicts. It must retain provenance and respect executive access permissions.
9. Authorized human leaders approve, revise, or override. Record the actor, time, evidence, reason, and outcome.
10. Initially staff execute approved actions in existing systems. Future write-back requires explicitly authorized tools and controls.

Model choice and commercial license are undecided. Evaluate candidate open-weight models on actual tasks and available hardware before choosing. Start with retrieval from approved records; fine-tuning/LoRA is a later option if evaluations show a need. Do not promise numerical speed or accuracy gains without measurements. A local model can still hallucinate; report unsupported conclusions as unknown and surface missing/conflicting evidence.

Local AI does not mean all original systems are local: cloud PMS/POS integrations still need network access. Plan for stale-data indicators and failures. Do not promise fully offline operation without defining which workflows work offline.

Hotel-controlled side: operational database, model serving, reports, access enforcement, audit records. Vendor subscription side: licensing, signed updates, support; avoid requiring guest records for billing. Remote support and telemetry must be explicit and controlled.
